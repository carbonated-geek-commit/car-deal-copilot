# Design — T-007: Offer extraction v1 (`packages/offer-extraction`)

- **Task:** `tasks/T-007-offer-extraction-v1.md`
- **Spec basis:** `specs/00-shared-core-architecture.md` — "Comms aggregation layer (provider-agnostic — shared)" ("Offer extraction: transcript/text/email → parsed `Offer` (price, fees, APR, term, monthly)"), "Core domain model", "Async backbone (shared)"; `specs/01` (transcribe-only posture — the extractor sees transcripts, never audio); `specs/02` (aggregation/extraction is the shared core value — no B2B-specific shape)
- **ADRs honored:** ADR-001 (Node/TS; spine defined once, no parallel types), ADR-002 (`payment_packing` canonical — this package never touches flag vocabulary), ADR-003 (npm workspaces), ADR-004 (`@deal-copilot/*` npm names, bare import aliases)
- **Upstream design honored:** `docs/design/T-001.md` — §2 spine types, §4 event contracts (`offer.extraction.requested/completed.v1`), §5.2–5.3 ack-then-queue and consumer idempotency rules
- **Stage:** design → build
- **Scope:** one pure library package. No I/O, no provider knowledge, no threading/storage/eventing, no LLM calls. T-009 (comms service) is the only intended caller.

| D2 | **Result is a discriminated union** (`{found: true; offer} \| {found: false}`), not `Offer \| undefined`. "No offer present" is a first-class terminal outcome (mirrors `OfferExtractionCompletedV1.offer?` and core's `AdapterResult` style) and the shape can later carry diagnostics (matched-rule provenance for a separately-approved LLM-assisted v2) without a signature break. `ExtractionInput`/`ExtractionResult` are this package's own API types — they reference spine types, never redefine them. | AC-2; ADR-001 "no parallel type definitions"; T-001 §4 event contract. |
| D3 | **The extractor always emits `flags: []`.** Flag emission is the flag engine's job (T-002) — this package never populates, invents, or interprets flag names. The field appears only because the canonical `Offer` requires it. | specs/00 "Flag engine" (consumes an Offer, emits flags); ADR-002 (flag vocabulary lives in core/T-002). |
| D4 | **`extractOffer` is total: it never throws, on any string input.** Garbled, empty, adversarial, or non-language input yields `{found: false}` or a partial offer — never an exception. Rationale: the caller is an event-bus consumer under at-least-once delivery; a throwing extractor turns one weird dealer SMS into a poison message and a dead-letter (T-001 §5.3), i.e. a delayed/dropped dealer signal. Totality keeps "no offer" distinguishable from "consumer crashed". | specs/00 "Provider timeouts must never drop a dealer message" (extended to processing: no message may poison the pipeline); T-001 §5.3. |
| D5 | **Precision over recall.** A field is populated only when a rule matches its value with an unambiguous label/context; ambiguous numbers are omitted rather than guessed. A fabricated `sale_price` feeds the flag engine and the walk-away comparison with fiction — worse than a gap, which the thread rollup (T-009) can fill from a later message. | specs/00 flag engine is a "pure function of Offer + qualified-rate + walk-away" — garbage in poisons it; AC-4's partial-offer support makes omission safe. |
| D6 | **Money/number conventions (v1):** all money parses to integer `MoneyCents` ("$23,500" → 2350000; "23.5k" → 2350000; "$450/mo" → 45000 as `monthly`). `apr` stays a percent number (6.9), matching core's doc comment. `term_months` normalizes years→months ("6 years" → 72). Monthly-vs-price disambiguation is context-token-driven (`/mo`, "per month", "a month" ⇒ monthly; "price", "OTD", "out the door", "sale" ⇒ price). An OTD total quoted **without** a breakdown maps to `sale_price` with `fees: []` (v1 simplification — v1 does not attempt to decompose bundled totals). Fee line items with an explicit label and amount ("doc fee $899") become `OfferFee` entries, `name` as written (trimmed). | specs/00 "Offer extraction" field list; T-001 §2 `MoneyCents` ("all money in the spine is integer cents"); rule-based-v1 scope per ADR-001 "Alternatives considered". |
| D7 | **Fixtures are synthetic.** The checked-in corpus contains no real persons, phone numbers, VINs tied to real vehicles, or real dealership identities — realistic in register, fabricated in content. The corpus is data (JSON), the test is a generic runner, so growing coverage never means writing new test code. | AC-5 (offline corpus); CLAUDE.md reporting posture (durable state in files); privacy hygiene consistent with T-001 §5 "never logged: bodies, phone numbers". |

## 2. Public API (exact signatures — `src/index.ts`)

The spine is referenced, never redefined: every domain shape below is an import from `@core`.

```ts
import type { MessageChannel, Offer } from '@core';

/**
 * Channel-agnostic extraction input (AC-3). One entry point for all three
 * channels of Message.channel; `text` is whatever the Message carries:
 *   call  → Message.transcript
 *   sms   → Message.body
 *   email → Message.body
 * `channel` is a normalization HINT (§4.1), never a router to different
 * extractors and never a carrier of provider knowledge.
 */
export interface ExtractionInput {
  channel: MessageChannel;
  text: string;
}

/**
 * Discriminated outcome. `found: false` is a valid terminal result — the
 * text contained no offer — not an error (mirrors
 * OfferExtractionCompletedV1.offer being absent, T-001 §4).
 */
export type ExtractionResult =
  | { readonly found: true; readonly offer: Offer }
  | { readonly found: false };

/**
 * Rule-based v1 extractor.
 * Pure, synchronous, deterministic, total (never throws — D4).
 * No I/O, no provider knowledge, no LLM calls, no logging.
 * `offer` is the canonical @core Offer with only confidently-extracted
 * fields populated (partial offers per AC-4; requires D1's core
 * amendment — see §0) and always `flags: []` (D3).
 */
export function extractOffer(input: ExtractionInput): ExtractionResult;
```

That is the entire public surface. No class, no config object, no async: configuration would imply per-caller behavior drift (two callers extracting different offers from the same text breaks determinism-as-idempotency, §5.3), and async would invite I/O into a package whose value is that it cannot do any.

## 4. Extraction behavior contract (rule-based v1)

No implementation code here — this is the behavior the builder implements and the corpus verifies.

### 4.1 Normalization (channel hint)

One shared rule core; per-channel pre-cleaning only:

- **email:** strip quoted reply chains ("On … wrote:", `>` blocks) and signature blocks so a stale offer quoted back by the buyer isn't re-extracted as the dealer's new offer; collapse HTML-ish whitespace artifacts.
- **call (transcript):** collapse filler/disfluency tokens; join spelled-out numbers ("four fifty a month") into numeric form where unambiguous.
- **sms:** minimal — trim, collapse whitespace.

After normalization, the same field rules (§4.2) run for all channels — channel never changes *what* is extractable, only text cleanup.

### 4.2 Field rules (all subject to D5 precision gate, D6 conventions)

| Field | Populated when | Omitted when |
|---|---|---|
| `sale_price` | A money amount with price context (price/OTD/sale/vehicle-cost tokens), or the sole large money amount in an unambiguous offer sentence | Amount could be a trade-in value, payoff, MSRP-vs-discount fragment, or context is absent |
| `monthly` | Money amount with per-month context | "$450" bare, no periodicity context |
| `apr` | Percent with rate/APR/financing context, plausibility-bounded (0 < apr < 50) | Percent that reads as discount, down-payment %, or out of bounds |
| `term_months` | Integer with months/years term context, normalized to months, plausibility-bounded (12–120) | Bare integers (mileage, stock numbers, years-as-model-year) |
| `fees[]` | Labeled fee line items (doc/dealer/destination/prep/title/reg + amount) | Unlabeled amounts; totals (those compete for `sale_price` per D6) |

`found: true` requires **at least one** of `sale_price`, `monthly`, `apr`, `term_months`, or a non-empty `fees[]` — otherwise `{found: false}`. A message that is pure logistics ("see you at 3, ask for Dave") yields `{found: false}` even though it contains digits.

### 4.3 Determinism, totality, bounds (binding on the builder)

- **Deterministic:** same `ExtractionInput` → deeply-equal `ExtractionResult`, always. No randomness, no clock, no locale dependence (parsing is fixed to en-US number formats in v1).
- **Total:** never throws (D4). The corpus includes hostile inputs to prove it.
- **Bounded:** all matching is effectively linear in input length — no nested-quantifier/catastrophic-backtracking regex patterns (the builder must review every pattern for this; the corpus includes a large-input fixture with a wall-clock sanity budget). This function runs on the bus consumer path, but "cheap and predictable" is still load-bearing: a ReDoS-able extractor is a poison-message factory.
- **Non-mutating:** input is read-only; every result is a fresh object (the receipt trail's append-only posture starts with nobody holding mutable references into message-derived data).

## 5. Error paths per operation

This package has exactly one operation, `extractOffer`, and it is pure — it has no I/O failure modes by construction. The table covers the operation itself, then the event-flow context it is designed to sit inside (so the T-009 designer/builder inherit one consistent story; the normative source for handler behavior remains T-001 §5.2–5.3).

### 5.1 `extractOffer` (this package)

| Condition | Behavior | Retry / idempotency | Logged | Surfaces as |
|---|---|---|---|---|
| Text contains a full offer | `{found: true, offer}` all fields populated | Pure + deterministic ⇒ re-running is harmless and identical | **Nothing — this package never logs** (message text is PII-laden: names, callbacks, numbers; T-001 §5.3 forbids logging bodies. A no-logging library cannot violate that.) | T-009 attaches to `Message.extracted_offer`, rolls into `current_offer`, flag engine runs downstream |
| Partial offer (e.g. monthly-only SMS) | `{found: true, offer}` with only known fields (AC-4; D1) | Same | Same | Partial rolls into `current_offer` per T-009's merge policy |
| No offer / logistics chatter / empty or whitespace text | `{found: false}` — terminal, not an error | Same | Same | `OfferExtractionCompletedV1` without `offer`; thread unchanged |
| Ambiguous numbers (bare "$450") | Field omitted (D5); possibly `{found: false}` overall | Same | Same | Gap, fillable by later messages via rollup |
| Garbled/hostile/huge input | `{found: false}` or partial; **never a throw** (D4), bounded time (§4.3) | Same | Same | Same as no-offer |
| Extractor bug throws despite D4 | Contract violation — a defect, not a path | Caller's consumer treats it as poison → bounded redelivery → DLQ with envelope intact (T-001 §5.3); the corpus totality tests exist to make this unreachable | Consumer logs `event_id`, `type`, `deal_id`, attempt count — never the text | Operator DLQ alert; **never a silent drop** |

### 5.2 Event-flow context (T-009's side of the seam — stated here so the seam is unambiguous)

- **Placement:** extraction runs **only** as an event-bus consumer: `offer.extraction.requested.v1` → `extractOffer` → publish `offer.extraction.completed.v1`. specs/00's rule — "webhooks ack immediately, all heavy work (transcription, extraction) runs on the event bus" — means **T-009 must not call `extractOffer` inside a webhook handler before ack, even though it is synchronous and cheap.** Ack-then-queue is T-009's handler sequence (T-001 §5.2: parse → durably enqueue → 2xx); this package protects the rule *by construction*: it exposes no webhook surface, no async, no bus client, and nothing to ack — it is incapable of acking or queueing, so it can never do them in the wrong order.
- **Retry/idempotency:** delivery is at-least-once, unordered. Determinism (§4.3) makes redelivered extraction requests yield byte-identical results; the dedupe anchor is the envelope `idempotency_key` (`deal_id:provider_message_ref:extraction` derivation, fixed by T-001 §5.3) — owned by producers/consumers, not by this package, which is stateless and holds no keys.
- **What is logged, where:** consumers log envelope metadata + outcome (found/not-found as a boolean, attempt count); never `text`, never extracted amounts alongside identifying refs beyond what T-001 §5.3 permits. This package contributes nothing to logs (§5.1).
- **What surfaces to users:** a found offer surfaces as the message's extracted offer and the thread's `current_offer` (and any flags the flag engine then raises → `alert.dispatch.requested.v1`). A not-found is invisible to the user — the message itself still threads normally; extraction silence never blocks message capture.

## 6. Fixture corpus & test design (AC-5)

**Fixture format** (one JSON file per case, D7 — synthetic content only):

```jsonc
{
  "name": "sms-monthly-only",
  "channel": "sms",
  "text": "Good news! We can get you to $389/mo. When can you come in?",
  "expected": { "found": true, "offer": { "fees": [], "monthly": 38900, "flags": [] } }
}
```

`expected` is compared as a deep-equality assertion against the full `ExtractionResult` (absent fields must be absent — asserting omission is how D5 is enforced, not just presence).

**Corpus coverage (minimum set; builder extends freely — runner is generic):**

| Group | Cases |
|---|---|
| transcripts | full offer (price+APR+term+monthly); spoken numbers ("four fifty a month"); call with no offer (scheduling); disfluent/garbled transcript |
| sms | monthly-only partial (the AC-4 example); price-only; bare-number ambiguity → omitted; logistics/no-offer; empty string |
| email | full offer with itemized fees (doc/dest/prep); quoted-reply chain containing a stale offer — only the new content extracts; OTD-total-only (D6 mapping); marketing blast with prices but no deal-specific offer (expected `found: false` — hard case, documents the precision stance) |
| hostile | very large input under time budget; binary-ish garbage; digits-everywhere non-offer (VIN + stock# + phone#) — all must not throw (D4) |

**Unit tests** (beside the corpus): money parsing table (D6 conventions, including "23.5k", cents-exactness), term normalization, monthly/price disambiguation tokens, determinism spot-check (`extractOffer(x)` twice → deep-equal), and a type-level assertion that the returned offer is the `@core` `Offer` (no parallel type — `expectTypeOf` against the import).

All offline: no network, no timers, no filesystem beyond vitest loading fixtures. From root: `npx vitest run packages/offer-extraction`.

## 9. Blockers / deviations

**No design blockers** — the design required no frozen-spine (specs/**) change and no unapproved integration.

**One resolved-by-escalation-path deviation, open for the chief (D1, §0):** AC-2+AC-4 jointly require `Offer.sale_price` to be optional; `packages/core` as built (T-001) has it required. Resolution is a chief resolve-and-log ADR plus a one-line amendment inside T-001's ownership (`sale_price?: MoneyCents`, with the flag-engine ripple noted), **before T-007's build merges**. The design is complete under either the primary resolution or the documented fallback (derived `ExtractedOffer` alias, §0 D1) — the builder must confirm which ADR landed before finalizing the one affected type name, and escalate if neither has.
