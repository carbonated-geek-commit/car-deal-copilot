## 0. Interpretive calls made by this design (drift trip-wire log)

Every call below sits inside spec/ADR ambiguity or is a mechanical consequence of a frozen file. A builder who finds any of them insufficient **stops and messages the lead** — it does not improvise, does not add a dependency, and does not edit a foreign file.

| # | Call | Basis / consequence |
|---|------|---------------------|
| **D1** | **A deal is created by `PUT /deals/:deal_id` with a caller-chosen id, not `POST /deals`.** | T-019's write seam is `StoreSessionFactory.forDeal(handle)` and a `DealHandle` is minted **only** by the `dealGate` `preHandler`, which reads `:deal_id` from validated params (`auth/deal-gate.ts`). A `POST /deals` has no `:deal_id`, therefore no handle, therefore **no reachable store** — creation is literally inexpressible through the foundation's only door. `PUT` on the caller's id restores it, satisfies the boot audit (validation + gate present), and makes creation idempotent by its natural key at zero cost (T-019 D8: "the spine's existing natural keys", no new idempotency ledger). `owner_id` is taken from the handle's scope and **never** from the body, so a created deal always belongs to the caller. §8.2 records the E3 consequence: a real gate must permit `write` on an id that does not exist yet. |
| **D2** | **Every identifier this API mints is DETERMINISTIC — derived from data the caller already supplied. Nothing is random.** `receipt_bundle_id = "receipt:<deal_id>"`; `VehicleInstance.id = "vi:<deal_id>:<dealership_id>"`; `Dealership.id = "dl-<slug>-<fnv1a32>"` over migration `0004`'s natural key tuple. | Two forces meet here. (a) T-019's static-invariant suite pins the import allowlist for `services/api/src/**` to `fastify, zod, node:process, @core, @comms, @db, @object-store, @receipt, @store-pg` — `node:crypto` is not on it, so `randomUUID` is unavailable without changing a foreign test. (b) Determinism is *better* than a generator here: a replayed `PUT` produces byte-identical ids, so idempotency is a property of the data rather than of a remembered key. One instance per thread is the spine's own cardinality (`DealerThread.vehicle_instance` is singular), so the thread key *is* the instance key. The `Dealership` slug is a pure FNV-1a-suffixed normalization of `(lower(name), upper(state), lower(city), zip_code)` — the exact tuple `packages/db/migrations/0004_dealerships_global.sql` makes unique — so find-or-create converges on one global row, which is the point of a shared directory. `new_id` stays injectable for the epic that wants uuids (§8.4). |
| **D3** | **A `VehicleInstance` submission carries `make` and `model` at the WIRE only. They are compared against the deal anchor and then DISCARDED — they are never stored, because `@core.VehicleInstance` has no field for them.** | This is the whole mechanism of AC-3. `packages/core/src/domain.ts`: "Deliberately carries NO make/model: those are the deal's anchor, so a thread that contradicts the anchor is unrepresentable. Builders must not add them." A mismatching instance therefore **cannot exist downstream**, which means the check has exactly one correct home: the API boundary, before the value is narrowed into the spine type. Matching case: the two fields are dropped and the stored instance is the spine shape unchanged. |
| **D4** | **Make/model comparison is case- and whitespace-insensitive (`trim().toLowerCase()`), and nothing else.** No synonym table, no fuzzy match, no VIN decode. | Q16: "VIN is **user-entered and unvalidated** at launch"; specs/01 backlog 4 keeps decode validation out. A fuzzy match would silently accept a substitution ("Chevy" vs "Chevrolet" is a judgement call the product has not made), and a byte-exact match would reject the buyer's own re-typing of their own anchor. Normalizing whitespace and case is the only transformation that cannot change *which vehicle* is meant. |
| **D5** | **The mismatch rejection is `422 unprocessable`; the write-once rejection is `409 conflict`.** | `errors/envelope.ts` fixes the vocabulary: `conflict // 409 — write-once / uniqueness violated`, `unprocessable // 422 — well-formed but violates a domain invariant`. A make/model mismatch is a well-formed request whose *content* contradicts an invariant; a `target_vehicle` write after lock is the write-once case the code comment names. T-019 §5.6's prose said `422` for the write-once case while its own code table says `409`; the code table wins because it is the shipped artifact, and §8.3 records the discrepancy for the lead. |
| **D6** | **The rejection response does NOT echo the VIN. The client highlights the vehicle it just submitted; the VIN is written to the RECEIPT TRAIL, which is where the spec requires it to be durable.** | `toEnvelope` (T-019, foreign file) **strips `details` for every code except `invalid_request`** and its `ApiFieldIssue` contract is "WHY, never WHAT … never the rejected value". There is no field in the shared envelope that can carry a VIN, and inventing a second error shape is exactly what AC-16 forbids. What AC-3 actually needs is preserved: the caller holds the VIN it just sent (so the red highlight is renderable), the response message names the remedy ("open a new deal for this vehicle"), and `GET /deals/:deal_id/receipt` returns the durable entry naming the VIN, so a reload or a second operator still sees which vehicle was refused. §8.3 records the alternative (a `context` map on the envelope for 4xx domain codes) as an ADR-sized, T-019-owned change if the lead wants the value on the wire. |
| **D7** | **The rejection receipt entry is a `note`, `direction: 'internal'`, authored by the account-side actor, with a machine-readable `[system]` prefix in the body.** | `packages/receipt/src/contract.ts` fixes `ReceiptEntryKind` to a closed set — `note | sms | email | call_meta` — and `NoteEntryInput.author` to `Exclude<MessageAuthor,'dealer'>`. There is no `system` kind and no `system` author, and adding one is an edit to a package this task does not own. `note`/`internal` is the honest slot: the receipt layer's one hard rule is that self-authored evidence never acquires a `dealer` label, and this entry is account-side by construction. The `[system]` prefix keeps it from reading as buyer prose. §8.5 recommends the lead consider a `system` author for the receipt vocabulary. |
| **D8** | **The rejection receipt is appended in its OWN unit of work, after the mutating session has been abandoned — never inside it.** | `packages/db/migrations/0014_target_vehicle_write_once.sql` says it outright: the write-once violation raises `DC002` and "record the rejection as a receipt event, which is a SEPARATE insert outside the aborted transaction". An append inside the failing transaction is rolled back with it, and the substitution attempt vanishes — the exact outcome Q11's rationale exists to prevent. Handlers therefore detect the violation on the read, roll the session back with nothing written, then append through `container.receiptsFor(handle.scope)`. |
| **D9** | **`unevaluable` is derived in `src/routes/**` from INPUT PRESENCE, and its equality with `@flag-engine`'s answer is pinned by a parity test in `test/routes/**`, which is where `@flag-engine` is imported.** | T-019's static suite forbids `@flag-engine` in `services/api/src/**` (D10 there: "the API computes nothing the domain already owns") and that rule is right about **verdicts**. But `unevaluable` is not a verdict — it is ADR-005's statement about which inputs the API *could not supply*, which is a fact this service owns. Deriving it in `src/` keeps the production path verdict-free and the foreign test untouched; importing `@flag-engine` in `test/routes/evaluability-parity.test.ts` (my ownership; the static scan walks `src/` only) makes drift a **test failure** rather than a silent divergence: the parity case runs the whole input matrix through `evaluateOffer` under a matrix of configs and asserts set equality with the API's derivation. |
| **D10** | **The API surfaces THREE per-flag states — `flagged`, `unevaluable`, `not_evaluated` — and NEVER a "clear"/"passing"/"fair" state.** | `services/comms/src/rollup.ts` (`flags: [], // rule 3 — always empty in this service`) and `packages/offer-extraction/src/extract.ts` (`flags: [], // D3: always empty`) mean **no stored `Offer` in this epic carries a flag**. Reading an empty `flags[]` as "evaluated, nothing fired" would report every offer as fine — precisely what specs/00 forbids ("never as 'fine'") and what ADR-005 §2 calls the distinction that must be preserved. `Offer` has no evaluation provenance field, so "evaluated and did not fire" is *unrepresentable in the spine*, and the API says `not_evaluated` rather than pretending. §8.6 escalates the underlying gap: nothing in the pipeline runs the flag engine yet. |
| **D11** | **`over_walkaway` and `above_market` are surfaced in two SEPARATE objects (`budget` and `fair_price`) with separate reasons, and no response type in this task has a field that fuses them.** No ranking, no score, no ordering is exposed. | specs/00 "Budget ceiling vs. fair price" is a two-question table; specs/01 W2 asks for a budget-ceiling tracker **and** a per-car fair-price verdict as distinct furniture. The task note allows leaving ranking out if it is a UI concern: it is. Ranking must be value-adjusted (specs/00 Consequences bullet 3), and a value-adjusted ordering is unbuildable while every fair-price answer is `unevaluable` (D10) — a half-version would be an invented verdict. The API ships the per-thread inputs an ordering needs and no ordering. |
| **D12** | **`DealerThread.dealership_id` is the thread's identity and is NOT mutable. AC-9's "allow updating" is satisfied by the create/bind route that SETS it.** | The store key is `(deal_id, dealership_id)` (`@comms` `resolveOrCreateThread`; `@store-pg` `CONSTRAINTS.thread_per_dealership`; migration `0007`), there is no delete on any port, and the boot audit refuses `DELETE` outright. A mutable `dealership_id` would mean moving a thread's messages — evidence — under a different dealership's name, which is the one thing an append-only trail must not permit. Correcting a mis-entered dealership is a new thread. |
| **D13** | **`author` on a note is REQUIRED from the caller and is additionally CHECKED against the account context's role; a claim the session cannot back is `403 forbidden`.** `owner ⇒ buyer`, `concierge_agent ⇒ concierge`. | Two rules meet: AC-8/specs/00 (`author` is "never inferred" — so it may not be defaulted) and `@comms/notes.ts` ("From the authenticated session on the write path, NEVER from a request body"). Requiring **and** verifying satisfies both: the caller states the author (nothing is inferred), and the API refuses an authorship the session cannot support (nothing is fabricated). `403` is T-019's reserved code for a role denial *inside* an owned account, which is exactly this. In E2 `role` is always `owner`, so a body claiming `concierge` is refused — correctly, because no concierge grant exists yet. |
| **D14** | **There is no `POST /offers`. An offer enters the system only by extraction from a message.** | ADR-006 puts the rollup in `@comms/rollup.ts` ("the blast radius is rollup.ts alone") and specs/01 W2 makes entry "notes-first — the buyer types what was said and the extractor parses the offer out of it". A direct offer write would be a second producer of `current_offer` that bypasses the newest-wins accumulation, i.e. a second answer to ADR-006's question reachable only through the API. Offers are read-only on this surface. |
| **D15** | **`Dealership` is create-or-find only. There is no update route and no delete route on the global record, and no route anywhere returns a contact outside an account-owned deal thread.** | specs/00 "Dealership data tenancy" + Q12 AMENDED. The global table is writable by every account, so an *update* path is a cross-account mutation surface (one account renaming another's dealership); find-or-create by the natural key is additive only. On the private half, `@core.DealershipContact` has no id and no account field — it exists only embedded in `DealerThread.working_with` — so "a contact endpoint" is necessarily a thread endpoint, and a global contact route is not merely forbidden but unrepresentable. |
| **D16** | **This task adds NO health endpoint.** `/healthz` and `/readyz` already exist on T-019's health plane (`http/health.ts`, registered by `buildServer`). | T-019 D6 put them on a plane with no account context and no store deliberately. A second health route inside the api scope would be a second contract for the same question, behind an account-context hook that a probe cannot satisfy — a readiness probe that returns `401` is worse than none. The war-room read surface AC-1 asks for is `GET /deals/:deal_id/war-room` (§3.3), not a health route. |

### 2.2 The two ports this task declares (and why they are not spine types)

```ts
/** The natural key migration 0004 makes unique. Global — there is no account here. */
export interface DealershipNaturalKey {
  readonly name: string;
  readonly state: string;
  readonly city: string;
  readonly zip_code: string;
}

/**
 * The GLOBAL directory (specs/00 "Dealership data tenancy"; Q12 AMENDED).
 *
 * `@comms`'s `CommsStore` has no dealership method and `@store-pg` "never
 * writes `dealerships`" (T-017 D15: "Account provisioning is an API/E3 concern;
 * minting a dealership … is the caller's responsibility"), so this seam is the
 * API's to declare — and declaring it HERE, with no account parameter on any
 * method, is what makes an account-scoped dealership read inexpressible. §8.4
 * asks the lead for the durable implementation's home.
 */
export interface DealershipDirectory {
  get(dealership_id: string): Promise<Dealership | undefined>;
  /** Find-or-create by the natural key. Never updates an existing row (D15). */
  ensure(key: DealershipNaturalKey): Promise<{ dealership: Dealership; created: boolean }>;
  /** Prefix search over name, bounded by the caller's limit. Global read. */
  search(q: string | undefined, limit: number, cursor?: string): Promise<{ items: readonly Dealership[]; next_cursor?: string }>;
}

export function createInMemoryDealershipDirectory(seed?: readonly Dealership[]): DealershipDirectory;

/**
 * ADR-007's input: THIS car's own snapshot. Keyed by `VehicleInstance.id`, never
```

## 4. Error paths per operation

### 4.1 The pipeline every route inherits (T-019 §4.2, unchanged)

`request_id` → body limit / content type (`413`/`415` through the envelope) → **account context** (`401`) → **validation** (`400` + `details[]`) → **deal gate** (`404`/`403`) → handler → projection + forbidden-field + no-`null` guard (`500` on a leak) → the single error handler. This task adds no hook and no ordering.

### 4.2 Per-operation table

| Operation | Failure mode | Status / code | Retry & idempotency | Logged | Surfaced |
|---|---|---|---|---|---|
| `PUT /deals/:deal_id` | deal exists, body differs | `409 conflict` | not retryable — `PATCH` instead | `warn` `deal_create_conflict` + deal_id | code + static message |
| `PUT /deals/:deal_id` | deal exists, body identical | `200` | **idempotent replay** — nothing written | `info` `deal_create_replay` | the stored `DealView` |
| `PUT /deals/:deal_id` | session commit `unavailable` | `503 unavailable` | **retry-safe**: the id is the natural key; a replay converges | `error` + SQLSTATE class | `retryable:true` |

### 4.3 Idempotency posture

The API still introduces **no request-level idempotency ledger** (T-019 D8). What makes each retry safe:

- **`PUT` routes** — the URL *is* the key (`deal_id`, `(deal_id, dealership_id)`), and D2's deterministic ids mean a replay produces byte-identical state. Re-sending is a no-op, not a duplicate.
- **`POST /deals/.../messages`** — `client_note_ref` is `@comms`'s anchor; `appendMessage` is keyed and returns `duplicate`. A `503 recorded_extraction_deferred` is explicitly *not* a failure and must be retried with the same ref.
- **`POST /dealerships`** — the natural key is the identity; find-or-create is idempotent by construction and never mutates.
- **Rejection receipts** — deliberately *not* deduplicated unless the caller supplies `client_attempt_ref` (§3.4).

### 4.4 Two failure orderings that are contracts, not preferences

**Rejection before receipt, receipt outside the session (D8).** A rejecting handler: opens the session → reads the deal through `ScopedReadModel` → detects the violation → **rolls back with nothing written** → appends the receipt entry through `container.receiptsFor(handle.scope)` in its own unit of work → throws the `ApiErrorException`. Appending inside the doomed transaction would roll the mark back with the write (migration `0014`'s comment says so in as many words), and appending *before* deciding would mark a rejection that might not happen.

**A failed mark does not become a retryable response.** If the receipt append itself fails, the response stays `409`/`422` and the failure is logged at `error` as `receipt_append_failed` with the deal id. Returning `503` would tell the client to retry a write that can never succeed, and swapping the code would hide a correct rejection behind an infrastructure problem. The lost mark is an operational alert, and §8.5 records that a durable outbox for it is a later epic's work. The same rule covers a deal with no `receipt_bundle_id`: the rejection still returns, and `receipt_bundle_missing` is logged at `error` — deals created through `PUT /deals/:deal_id` always have one (D2).

### 4.5 Read-modify-write, and what it costs

`@comms`'s `CommsStore` offers no partial update: negotiation state is written with `putThread(deal_id, thread)` and deal-level fields with `putDeal(deal)` — both "seed/replace". Every mutating handler therefore: opens one `StoreSession` (one transaction in Postgres mode), **re-reads inside it**, applies the narrowest possible change, and writes the aggregate back with `dealer_threads`, `offers`, and `messages` carried through **unchanged** (`aggregate.ts`). Handlers never write a thread they did not just read.

This is correct at the aggregate level and lossy at the store-internal level: `InMemoryCommsStore.putThread` rebuilds a thread's rows with `message_ref: ''` and resets its `RollupState`. §8.7 escalates that in full — it is a seam between T-014 and this task, not a defect of any route, and it needs a `@comms`-owned fix.

### 4.6 Logging

Inherits T-019 §4.5's allow list unchanged. This task adds these event names and nothing else: `deal_create_replay`, `deal_create_conflict`, `target_vehicle_write_once_reject`, `vehicle_anchor_reject`, `year_drift`, `unknown_dealership`, `author_not_permitted_for_role`, `extraction_deferred`, `dealership_id_collision`, `receipt_append_failed`, `receipt_bundle_missing`.

**Never logged by any route:** a VIN, a note or message body, a `DealershipContact` name/phone/email, a dealership name, a rejected input value, a price or any money amount. The mismatch log names *which field* mismatched (`make` or `model`) and the ids — never the values. The VIN lives in the receipt trail, which is account-scoped storage, not in a log aggregator.

## 5. Invariant touchpoints, and how the design protects each

### 5.1 One deal, one make/model (specs/00 "Cardinality invariants"; Q11 AMENDED)

Four layers, each independently sufficient against a different failure:

1. **Type** — `@core.VehicleTarget.make`/`model` are `readonly`; `VehicleInstance` has no make/model at all. A thread that contradicts the anchor is unrepresentable *after* the boundary (D3).
2. **Schema** — `make`/`model` appear in exactly two request shapes (deal create, target-vehicle write) plus the wire-only claim. `PATCH /deals/:deal_id` cannot express them, so the common edit path cannot reach the invariant at all.
3. **Predicate** — the lock is `@core.isTargetVehicleLocked`, imported. `packages/core` names this task as its consumer and migration `0014` mirrors its three disjuncts in the same order; a static test asserts no rival predicate exists in `src/routes/`.
4. **Trail** — every rejection is a receipt entry (D7/D8), so a substitution attempt leaves a mark instead of vanishing.

### 5.2 Year drift is a soft guide (Q16, AC-5)

There is no code path from `yearDrift(...) !== undefined` to a non-2xx response — the function returns a *view*, not a decision, and it is consumed only by the war-room assembler. The test asserts the absence by exhausting the boundary years plus the no-range case and requiring `200` from all of them.

### 5.3 VIN is user-entered and unvalidated (Q16, AC-6)

The schema is `z.string().min(1).max(64).optional()` and nothing more: no checksum, no length-17 rule, no charset rule beyond a printable bound, and no decode call. The harness's adapter slots throw on any call, so "no endpoint gates acceptance on a decode lookup" is proven by the absence of a call rather than by inspection.

### 5.4 Dealership data tenancy (Q12 AMENDED, AC-10)

Global and private are separated by **shape**, not by a filter someone must remember:
- `DealershipDirectory` has no method that takes an account, so an account-scoped dealership read is inexpressible; `DealershipPublicView` (T-019's `Pick`) has no field a contact could occupy.
- `DealershipContact` has no id and no account field in the spine — it exists only as `DealerThread.working_with`, reachable only through a `DealHandle` the gate minted. There is no `/dealerships/:id/contacts` route, and a route-table test asserts that no path containing `contact` exists outside `/deals/:deal_id/...`.
- The global record has no update path (D15), so one account cannot rewrite a row another account relies on.

### 5.5 Budget ceiling vs. fair price stay two questions (Q20, ADR-007, AC-15)

`walk_away_number` is writable only on the deal and readable only from `DealView`; no thread, instance, or offer schema can express it. Every valuation-derived value is reached through a `VehicleInstance.id` (`ValuationLookup.snapshotFor`), never through make/model. The response splits them into `budget` and `fair_price` objects with their own reasons, and a static test forbids a key named `verdict`, `score`, or `rank` anywhere in `src/routes/`. The API selects no band: ADR-007 fixes `retail`, and the API never even reads a band — it hands the whole snapshot to the evaluability derivation, mirroring T-011 D8.

### 5.6 ADR-005 — unevaluable, never zero and never "not triggered" (AC-11, AC-12, AC-13)

`sale_price` absent stays an omitted key end to end (T-019's `omitAbsent` + the no-`null` guard). `unevaluable` is derived from input presence and parity-tested against `@flag-engine` (D9). And the third state, `not_evaluated` (D10), exists because nothing in this epic evaluates flags — so a thread with no valuation reports `above_market: unevaluable / no_valuation`, and a thread with everything present still never reports "fine".

### 5.7 ADR-006 — the rollup is `@comms`'s

`current_offer` is read from the read model and projected by T-019's `projectOffer`, never merged, recomputed, or reordered here, and there is no write path that sets it (D14). A test asserts the projected `current_offer` is byte-identical to the read model's.

### 5.8 Append-only receipt trail; no audio, no transcript

No route uses `DELETE`, and no `PUT`/`PATCH` names a `/messages`, `/receipt`, or `/notes` path — the boot audit refuses to start otherwise, and a test registers a violating fixture route to prove the refusal still fires with this suite loaded. `@receipt.ReceiptStore` has only `append` and `read`. `@core.Message` has no audio or transcript field to project, and `MessageView` is T-019's `AssertResponseSafe<Message>`, so reintroducing one would stop this package compiling.

### 5.9 Account ownership (T-019 AC-2, inherited)

Every route in this task that touches the store does so through a `DealHandle` — there is no other door (`StoreSessionFactory.forDeal`, `ScopedReadModel`). `owner_id` on create comes from `handle.scope.account_id` and is ignored if a body supplies it. The `/dealerships` routes touch no deal-scoped state at all, and the account context hook still runs on them (they live in the api scope), so an unauthenticated caller gets `401` before validation.

## 6. Test plan

Run from the repo root: `npx vitest run services/api/test/routes`. Typecheck: `npx tsc -p services/api --noEmit`.

- **Offline by default (ADR-008).** Every case runs against the in-memory container with no `DATABASE_URL` and no object-store config. There is no `.db.test.ts` in this task: these routes are storage-agnostic by construction (T-019 AC-8), and a Postgres-backed run belongs to whichever task builds `@store-pg`'s session — asserting it here would claim coverage this task cannot honestly provide.
- **Rejections are proven by state, not by status.** Every rejection case asserts three things: the status/code, that the stored aggregate is **unchanged**, and that the receipt trail gained exactly the expected number of entries.
- **Absence is asserted as absence.** `sale_price`, `vin`, `working_with`, `year_range` — each is checked with `expect(Object.keys(body)).not.toContain(...)`, not with `toBeUndefined()`, so a `null` regression fails.
- **Zero-store proxies.** Validation and authorization cases inject a `CommsStore` proxy that throws on any method, so "rejected before any repository call" is proven by the absence of a call.
- **Parity over duplication.** `evaluability-parity.test.ts` is the only file in the repo that imports `@flag-engine` into `services/api`, and it exists so the `src/routes/` derivation cannot drift from the engine (D9).
- **Boot-audit compliance is a test, not a hope.** `audit-compliance.test.ts` builds the real server with the real suite and asserts `auditRouteTable(app)` is empty, then registers a deliberately gate-less `:deal_id` route alongside the suite and asserts startup refuses.

## 8. Blockers / deviations

**One item (§8.1) requires a lead decision before this task's BUILD can land green.** Nothing here requires a spine change, an unapproved integration, or a spec edit, and the design above is complete and buildable as written.

### 8.1 T-019's static-invariant test fails by construction the moment this task creates its subtree — **needs the lead**

`services/api/test/static-invariants.test.ts` (T-019's file, not mine) contains:

```ts
it('creates no src/routes/** — that subtree belongs to T-020', () => {
  expect(readdirSync(SRC)).not.toContain('routes');
  expect(SOURCES.some((s) => s.name.startsWith('routes/'))).toBe(false);
  expect(readdirSync(join(SERVICE, 'test'))).not.toContain('routes');
});
```

It is a correct assertion *for T-019* and it becomes false the instant T-020 does its job. **T-020's builder must not edit it.** The lead needs to assign a one-case amendment to whoever owns that file — the natural replacement being the inverse: `src/routes/**` exists, and the foundation modules (`auth/`, `context/`, `errors/`, `validation/`, `projection/`, `http/`, `composition/`, `config/`, `webhooks/`) do **not** live under it. The suite's other `src/**` scans (import allowlist, forbidden vocabulary, one `DealHandle` mint site, one identity reader, one `process.env` reader) are all satisfied by this design as written — §1.1's import column and §1.2's own static test exist to keep them satisfied — so this is the only case that needs changing.

### 8.2 Deal creation needs a gate disposition that E3 must define (note)

D1 routes creation through `PUT /deals/:deal_id`, which passes `dealGate(gate, 'write')` on an id that does not exist yet. The E2 permissive gate allows it. A real E3 gate that denies `deal_not_found` would make deal creation impossible without touching a route. `DealAction` is T-019's type and I cannot add a `create` member, so this is flagged now rather than discovered during E3: **the E3 gate must permit `write` on an unknown deal id for an authenticated account, or T-019 must gain a `create` action.** Either is a one-file change in `auth/deal-gate.ts`, which is exactly where T-019 promised E3's diff would be.

### 8.3 What the shared error envelope cannot carry (note)

Two consequences of `errors/envelope.ts`, a file this task does not own:

1. `toEnvelope` strips `details` for every code except `invalid_request`, so a `422` cannot carry field paths and a rejection cannot carry the VIN (D6). If the lead wants the VIN on the wire for AC-3, that is an ADR-sized addition to the envelope (e.g. a `context?: Readonly<Record<string,string>>` permitted for 4xx domain codes) owned by T-019, not something a route may improvise.
2. T-019's §5.6 prose says the write-once rejection is `422` while its shipped `ApiErrorCode` comment says `409 — write-once / uniqueness violated`. This design follows the code (D5). Worth a one-line correction to T-019's design doc so the next reader does not have to choose.

### 8.4 The global dealership store has no durable home yet (note)

`@comms`'s `CommsStore` has no dealership method; `@store-pg` "never writes `dealerships`" (T-017 D15) while migration `0004` defines the table. So the API must own the seam, and this design declares `DealershipDirectory` in `src/routes/directory.ts` with an in-memory implementation — correct for the ADR-008 default posture, and a real gap for Postgres mode. **Recommendation:** a later task gives `@store-pg` (or a small `@directory`) the durable implementation behind this exact port, and reconciles D2's deterministic slug ids with `0004`'s `uuid` primary key — most cleanly by making the slug a stored `external_id` column rather than the primary key. Nothing in this design assumes the id format outside `directory.ts`.

### 8.5 The receipt vocabulary has no `system` author or kind (note)

`ReceiptEntryKind` is a closed set and `NoteEntryInput.author` excludes `dealer`, so a rejection event is recorded as an account-authored `note` with a `[system]` body prefix (D7). It is honest — the entry is account-side and never claims dealer provenance — but a reader must parse a prefix to distinguish a product-generated mark from buyer prose. **Recommendation:** the task that next owns `@receipt` considers a `system` author (or a `kind: 'system_event'`) so the distinction is typed. Related: §4.4's "a failed mark does not become a retryable response" leaves a small window where a rejection returns without its trail entry; a durable outbox for receipt appends is the proper fix and belongs to an epic that owns the queue.

### 8.6 Nothing in this epic evaluates flags (note — the reason `not_evaluated` exists)

`services/comms/src/rollup.ts` and `packages/offer-extraction/src/extract.ts` both hard-code `flags: []`, and no consumer calls `@flag-engine.evaluateOffer`. So every stored offer carries an empty flag list, and the war room can honestly report only `flagged` (never, today), `unevaluable`, or `not_evaluated` (D10). This design refuses to paper over it, because reading empty as "fine" is the exact failure specs/00 and ADR-005 name. **Recommendation:** a task that owns the extraction-apply consumer runs the flag engine (with the buyer's `walk_away_number`, prequal `qualified_apr`, and the instance's `ValuationSnapshot`) and stores the result. `Offer` has no field for "evaluated, nothing fired", so recording an evaluation may need a spine addition — a lead/ADR call, not a route's.

### 8.7 `putThread` / `putDeal` are seed-or-replace, and every negotiation-state write pays for it (note — highest-value follow-up)

`services/comms/src/ports.ts` states that mutating `process_step`, `working_with`, `vehicle_instance`, `target_vehicle`, or `walk_away_number` "belong[s] to the buyer through the API (T-019/T-020)" — but the only writes the port offers are `putDeal` and `putThread`, both of which rebuild the record. In `InMemoryCommsStore`, `putThread` re-creates a thread's rows with `message_ref: ''` and resets its `RollupState`, and `putDeal` rebuilds the whole deal record the same way. Consequences of a `PATCH process_step` on a live thread, stated plainly:

- the visible aggregate is preserved (this design carries `messages`, `offers`, and every untouched thread through unchanged — §4.5), so the API's own reads stay correct;
- but the store's correlation index is lost, so a later `attachExtractedOffer(deal_id, message_ref, …)` for an already-stored message returns `not_found` and that extraction result is dropped;
- and the thread's `RollupState` resets, so ADR-006's per-field newest-wins loses its provenance and a late-arriving older message can overwrite a newer field.

No route can avoid this: there is no partial-update method to call, and `@comms` is not this task's to edit. **Recommendation:** a `@comms`-owned method that updates negotiation state in place (e.g. `updateThreadState(deal_id, dealership_id, patch)`), or a `putThread` that preserves `refIndex` and `rollup` for an existing key. Until then, T-020's build should land a test that **pins the current behaviour** so the fix is verifiable rather than believed, and the lead should know that the shortest path to the bug in production is a buyer advancing a process step while an extraction is in flight.

### 8.8 Deliberate absences, recorded so they read as decisions (note)

- **No `GET /deals` (account deal list).** No port exposes a per-account deal listing; building one would mean an unscoped scan, which is the one thing T-019's seam refuses. specs/01 W1 (the dashboard) therefore has no API yet — it belongs with the account surface in E3.
- **No `POST /offers`** (D14), **no dealership update/delete** (D15), **no cross-thread ranking** (D11), **no second health endpoint** (D16), **no outbound send** (a later epic owns origination; `@comms`'s `OutboundPort` is type-only today).
- **`qualified_apr` is never available in E2**, so `rate_markup` is always `unevaluable / no_qualified_apr`. specs/01 "Credit data residency" allows only the prequal summary, and no prequal store is reachable; the lookup belongs to the credit epic. The API says so rather than defaulting the value, which is ADR-005 applied to the input it does not have.
