# Design — T-010: Spine v0.5 domain migration (`packages/core`)

- **Task:** `tasks/T-010-spine-v05-domain-migration.md`
- **Spec basis (authoritative, v0.5):** `specs/00-shared-core-architecture.md` — "Core domain model", "Cardinality invariants (structurally enforced)", "Budget ceiling vs. fair price — two different questions", "Dealership data tenancy", "Comms aggregation layer", "Flag engine", "Async backbone"; `specs/01-consumer-product-spec.md` — "Consent & recording posture"
- **Decisions honored:** `decisions/OPEN-QUESTIONS.md` Q11 (AMENDED), Q12 (AMENDED), Q14, Q16, Q20, Q22 (RATIFIED); ADR-001 (Node/TS, spine defined once), ADR-002 (`payment_packing` canonical), ADR-005 (`sale_price` optional / unevaluable-never-zero), ADR-006 (`current_offer` rollup), ADR-007 (`above_market` = retail band), ADR-008 (Epic-2 libraries; API defaults to in-memory)
- **Supersedes (within `packages/core` only):** `docs/design/T-001.md` §2–§4 type listings. T-001 §5 (error paths, retries, idempotency) remains the behavioral baseline; §5 of this document is the v0.5 delta and takes precedence where the two differ.
- **Stage:** design → build
- **Scope:** types + contracts + pure total helpers inside `packages/core/**` (plus this package's own tests). No I/O, no persistence, no provider logic, no root-config edits (T-015 owns those).

**Ownership boundary.** This design changes files under `packages/core/**` only. It is a deliberately breaking change: `packages/flag-engine`, `packages/offer-extraction`, `packages/receipt`, `packages/adapters/*`, and `services/comms` will not typecheck until T-011…T-014 land. **No compatibility shims, no deprecated aliases, no re-exported `VehicleSpec`.** The migration tasks are the fix (task Notes; ADR-001 "no parallel type definitions").

## 0. Interpretive calls made by this design (drift trip-wire log)

Every call below stays inside spec ambiguity or is a mechanical consequence of a v0.5 spec line. None touches a protected path, none adds an integration, none changes the frozen spine's meaning. **A builder who finds any of these insufficient must stop and escalate — do not improvise an alternative.**

| # | Call | Basis |
|---|------|-------|
| **D1** | `VehicleInstance` gets a declared key field `id: string`. | specs/00 references the instance as `vehicle_instance_id (→ VehicleInstance)` from both `ValuationSnapshot` and `VehicleData`; a referenced entity must be addressable. Task note: "Declaring it is a mechanical consequence of the reference, not new scope." |
| **D2** | `Dealership` gets `id: string` (the task EXTRA names it); `DealershipContact` gets **no** id and **no** account field. | Task EXTRA + AC-5/AC-6 name the exact field lists. Contacts are *embedded* in the account-owned `DealerThread` (D3), so their account scope is structural rather than a field. Storage keys are T-016/T-017's business (§4.4). |
| **D3** | `DealerThread.vehicle_instance` and `DealerThread.working_with` are **embedded values**; `dealership_id` is a **reference**. | specs/00 `DealerThread` block uses `_id` for exactly one child (`dealership_id (→ Dealership, global)`) and bare names for the other two (`vehicle_instance`, `working_with`). The naming *is* the tenancy statement: the global thing is referenced, the private things live inside the account's own aggregate. |
| **D4** | `vehicle_instance?` and `working_with?` are **optional** on `DealerThread`. | `process_step` starts at `information_gather` — before the buyer knows which specific car or which person they are handed to. Requiring them would force fabricated data into a receipt trail whose whole value is that it is not fabricated (specs/00 "Receipt layer"). Absence is handled honestly: with no instance there is no `ValuationSnapshot`, so fair-price is **unevaluable**, never "fine" (specs/00 "Budget ceiling vs. fair price"; ADR-005 §2). The API layer (T-020) enforces "an offer-carrying thread names its car"; the type does not fabricate one. |
| **D5** | `ValuationSnapshot`'s four bands are **flat** (`wholesale?`, `trade_in?`, `retail?`, `private_party?`), not nested under `values`. | ADR-007 "Decision" refers to `ValuationSnapshot.retail` by that exact path — a binding ADR naming the shape. specs/00's v0.5 block also lists them as direct children. |
| **D6** | `ValuationSnapshot.fetched_at` → **`captured_at`**; `VehicleData.fetched_at` → **`captured_at`**. `VehicleHistorySummary` / `PrequalResult` keep `fetched_at`. | specs/00 v0.5 rewrote both model blocks and both now end `└── source, captured_at`. The two types are being rewritten wholesale anyway, so adopting the spec's own field name costs nothing. The other two types have no spec model block and are unchanged by v0.5 — renaming them would be churn with no spec line. |
| **D7** | `VehicleData.reliability?` is **not** added. | specs/00's v0.5 `VehicleData` block lists `reliability?`, but no spec line, ADR, or adapter anywhere defines its shape (specs/00 "Vehicle data" sources it from a "crowd-sourced repair ledger" that does not exist). Inventing a shape would be exactly the drift CLAUDE.md invariant 3 forbids. Omission is forward-compatible: an optional field is additive and non-breaking when a spec line arrives. |
| **D8** | `VehicleInstance.additions` is `string[]`. | specs/00 says "options, packages, dealer add-ons, accessories" and gives no shape. Free-text labels are the minimal non-inventive transcription of buyer-entered data. Priced add-ons already have a home on the offer (`OfferFee`), so nothing is lost. Structuring `additions` later requires a spec line or ADR. |
| **D9** | `CallMeta.duration_seconds` names the unit; `started_at` required, `duration_seconds?` / `party?` optional. | specs/00 writes "(started_at, duration, party)" without units; naming the unit follows the `MoneyCents` precedent (T-001 §2). A missed or in-flight call has no duration, and a blocked/unknown caller has no party — both must be recordable rather than blocking the call-metadata log the v0.5 comms flow requires. |
| **D10** | Extraction events carry `message_ref`, not `provider_message_ref`; `dealer_id` → `dealership_id` throughout the event surface. | v0.5 runs extraction on **notes** ("any message text — buyer note, SMS, or email"), and a note has no provider id. The anchor must be channel-neutral. `dealer_id` referred to a field (`DealerThread.dealer_id`) that no longer exists. `InboundComms` and `ProviderSendReceipt` keep `provider_message_ref` — those really are provider ids. |
| **D11** | `InboundComms.channel` is typed `Exclude<MessageChannel, 'note'>` and `InboundComms` gains `call_meta?` in place of `call_ref?`. | A note is authored in-app and can never arrive from a provider webhook; making that unrepresentable protects the author-honesty guarantee (specs/00 "Receipt layer": author "never inferred"; Q21 mitigation). `call_ref` existed to hand audio to transcription — with Q14/specs/01 there is no transcription and no audio, so a field pointing at a provider audio handle must go rather than sit around inviting re-wiring. The v0.5 flow needs call **metadata** instead ("log call metadata (time, direction, party)"). |
| **D12** | `ValuationRequest` becomes `{ target: VehicleTarget; instance: VehicleInstance }`. | `VehicleInstance` deliberately has no make/model (they are the deal's anchor), and specs/00 states "no valuation source can price *Honda Accord* without year, trim, mileage, and condition". Both halves are therefore required, and requiring an `instance` makes AC-10's "cannot be constructed against a bare make/model" structural. The adapter stamps `snapshot.vehicle_instance_id = request.instance.id`. |
| **D13** | Core exports frozen `readonly` vocabulary arrays for the v0.5 enums (`VEHICLE_CONDITIONS`, `DEALERSHIP_CONTACT_ROLES`, `PROCESS_STEPS`, `MESSAGE_CHANNELS`, `MESSAGE_DIRECTIONS`, `MESSAGE_AUTHORS`) alongside the existing `OFFER_FLAGS`. | ADR-008 puts `zod` at the API route boundary; without a shared vocabulary each validator would re-declare the enum, which is ADR-001's "parallel type definition" in a different syntax. One array per enum keeps the vocabulary defined once. Types are still the source: each array is `readonly T[]`. |
| **D14** | `AlertDispatchRequestedV1.kind` gains `'call_logged'`. | The v0.5 call flow is "log call metadata → **notify owner** → owner writes a note → extract on the note". That notification exists to *prompt a note*, which none of the three Epic-1 kinds expresses. Additive to a payload union; no other contract changes. |
| **D15** | `Message` still has **no** `id`, and no persistence annotations appear anywhere in core (T-001 D2 restated, still binding). | Correlation identifiers live in the event envelope and in the storage layer. If T-017 needs a domain-level message id, that is an ADR, not a quiet field addition. |
| **D16** | `Message.body` is **optional** (`body?: string`). | specs/00's ratified `Message` block writes `body` unqualified while explicitly marking `call_meta?` and `extracted_offer?` optional in the same block, so the omission of `?` is meaningful and this is a real call. It is made because `channel: 'call'` produces a message whose whole content is `call_meta` — there is no text. Requiring `body` would force `body: ''` into an append-only receipt trail, i.e. fabricated content in the one structure whose value is that it is not fabricated (specs/00 "Receipt layer"). Same species as D4: absence is typed as absence rather than faked. A call message with no note attached renders as "call logged, no note yet" — which is also exactly the state D14's `call_logged` alert exists to prompt the owner out of. If the chief prefers `body` required, the fix is one character plus a rule that a call message cannot be written until its note is. |
| **D17** | `VehicleData.decode?` is **retained** (carried forward from T-001) even though specs/00's v0.5 `VehicleData` block lists only `recalls[], history?, reliability?, captured_at`. | The block's own header line reads "(**decode**, recalls, history for one specific car)", and specs/00 "Vehicle data" sources decode from NHTSA vPIC — an approved, already-built integration (T-004). This is retention of a specified, wired field the v0.5 rewrite did not repudiate, not an invention. Contrast D7: `reliability?` is listed in the block but has no shape defined anywhere, so it is omitted. The asymmetry is deliberate — keep what is defined, drop what is only named. |

## 2. Domain types — `packages/core/src/domain.ts`

The **single definition** of the v0.5 spine (ADR-001). Downstream imports these through the bare `@core` alias and never re-declares them; nothing below may be copied, narrowed, or re-stated in another package.

### 2.1 Scalars and vocabularies

```ts
/** ISO-8601 UTC timestamp string. */
export type IsoTimestamp = string;

/** Integer USD cents. All money in the spine is integer cents — no floats. */
export type MoneyCents = number;

/**
 * VIN as the buyer typed it. Q16: user-entered and UNVALIDATED at launch — the
 * buyer's own record, not a lookup key. No decode-derived validation belongs
 * anywhere in this package (specs/01 backlog item 4).
 */
export type Vin = string;

export type DealPath = 'online' | 'hybrid' | 'in_person';
export type DealStatus = 'draft' | 'active' | 'negotiating' | 'closed' | 'burned';

/** specs/00 Message (ratified Q22): `note` = text the buyer/operator authored. */
export type MessageChannel = 'call' | 'sms' | 'email' | 'note';
/** `internal` = the buyer's/operator's own record, not a dealer exchange. */
export type MessageDirection = 'in' | 'out' | 'internal';
/** Who produced this text — NEVER inferred (specs/00; Q22; Q21 mitigation). */
export type MessageAuthor = 'dealer' | 'buyer' | 'concierge';

export type VehicleCondition = 'new' | 'used' | 'certified';

export type DealershipContactRole =
  | 'general_manager'
  | 'sales_manager'
  | 'finance_manager'
  | 'sales_agent';

/** How far along the negotiation with ONE dealership is (Q12). */
export type ProcessStep =
  | 'information_gather'
  | 'deal_negotiation'
  | 'deal_approval'
  | 'financing'
  | 'final_sale'
  | 'pickup';

/**
 * ADR-002: canonical name is `payment_packing`.
 * ADR-007: `above_market` compares the offer against THIS instance's own
 * `ValuationSnapshot.retail` band — distinct from `over_walkaway`, which is the
 * deal-level budget ceiling (Q20).
 */
export type OfferFlag =
  | 'payment_packing'
  | 'rate_markup'
  | 'junk_fee'
  | 'over_walkaway'
  | 'above_market';

// D13 — one shared vocabulary per enum; validators (zod, ADR-008) import these
// rather than re-declaring the literals.
export const OFFER_FLAGS: readonly OfferFlag[] = [
  'payment_packing', 'rate_markup', 'junk_fee', 'over_walkaway', 'above_market',
];
export const MESSAGE_CHANNELS: readonly MessageChannel[] = ['call', 'sms', 'email', 'note'];
export const MESSAGE_DIRECTIONS: readonly MessageDirection[] = ['in', 'out', 'internal'];
export const MESSAGE_AUTHORS: readonly MessageAuthor[] = ['dealer', 'buyer', 'concierge'];
export const VEHICLE_CONDITIONS: readonly VehicleCondition[] = ['new', 'used', 'certified'];
export const DEALERSHIP_CONTACT_ROLES: readonly DealershipContactRole[] = [
  'general_manager', 'sales_manager', 'finance_manager', 'sales_agent',
];
export const PROCESS_STEPS: readonly ProcessStep[] = [
  'information_gather', 'deal_negotiation', 'deal_approval', 'financing', 'final_sale', 'pickup',
];
```

### 2.2 Identity (provider-agnostic by construction — unchanged by v0.5)

```ts
/**

 * There is intentionally NO provider/provisioner/vendor field on this type, and

 */
export interface IdentityRef {
  identity_id: string;
  /** E.164 phone number, when the identity has one. */
  phone_number?: string;
  /** Email alias/inbox address, when the identity has one. */

}
```

### 2.3 Vehicle — the v0.5 split

```ts
/** Inclusive span. SOFT GUIDE only (Q16, specs/00 "Year drift"). */
export interface YearRange {
  from: number;
  to: number;
}

/**
 * What the buyer is shopping — the deal's comparison anchor.
 * `make`/`model` are `readonly`: write-once, settable while the deal is `draft`,
 * immutable once any offer is attached (specs/00 "Cardinality invariants").
 * `year_range` is NOT readonly — it is a soft guide the buyer may widen or
 * narrow, and nothing rejects an instance whose year falls outside it.
 */
export interface VehicleTarget {
  readonly make: string;
  readonly model: string;
  year_range?: YearRange;
}

/** The ONLY shape whose make/model are settable — used at deal creation (§2.7). */
export type VehicleTargetDraft = {
  -readonly [K in keyof VehicleTarget]: VehicleTarget[K];
};

/**
 * The SPECIFIC car one dealership is offering — varies per thread.
 * Deliberately carries NO make/model: those are the deal's anchor, so a thread
 * that contradicts the anchor is unrepresentable (§6, invariant I-2).
 * `id` (D1) is what `ValuationSnapshot.vehicle_instance_id` and
 * `VehicleData.vehicle_instance_id` point at.
 */
export interface VehicleInstance {
  id: string;
  /** User-entered, unvalidated (Q16). Absent is normal and not an error. */
  vin?: Vin;
  year: number;
  /** Trim may differ freely between dealerships. */
  trim?: string;
  /** Odometer miles; absent for new. */
  mileage?: number;
  condition: VehicleCondition;
  /** Options, packages, dealer add-ons, accessories — free-text labels (D8). */
  additions: string[];
}
```

### 2.4 Dealership — the tenancy split

```ts
/**
 * GLOBAL. One shared row per real dealership, referenced by any account's deals,
 * batch-loadable later (specs/00 "Dealership data tenancy"; Q12 AMENDED).
 * There is intentionally NO account/owner field and NO `staff[]` array — the
 * people were moved out of this record precisely so they cannot be redistributed.
 */
export interface Dealership {
  id: string;
  name: string;
  state: string;
  city: string;
  /** String, not number — leading zeros are real ZIPs. */
  zip_code: string;
}

/**
 * PRIVATE to the account that entered it; never global, never shared
 * (specs/00 "Dealership data tenancy"; Q12 AMENDED). It carries no account field
 * because it is embedded in the account-owned `DealerThread` (D2/D3) — there is
 * no free-standing, globally addressable contact record in the spine to leak.
 */
export interface DealershipContact {
  name: string;
  role: DealershipContactRole;
  phone?: string;
  email?: string;
}
```

### 2.5 Aggregate root and thread

```ts
export interface Deal {
  id: string;
  /** User in consumer, Org/Seat in B2B — core does not distinguish. */
  owner_id: string;
  path: DealPath;
  status: DealStatus;
  /** IMMUTABLE make/model once any offer attaches (§2.7, §6 I-1). */
  target_vehicle: VehicleTarget;
  budget: MoneyCents;
  /**
   * Q20: the buyer's BUDGET CEILING for the whole deal — the "can I afford it?"
   * number, compared against a thread offer's out-the-door total (`over_walkaway`).
   * It is NOT a fair-price judgement: that is per-instance, against that car's own
   * `ValuationSnapshot` (`above_market`, ADR-007).
   */
  walk_away_number: MoneyCents;
  /** Absent until first dealer contact (lazy provisioning, specs/01). */
  identity_ref?: IdentityRef;
  /** MANY dealerships, each offering its own specific car. */
  dealer_threads: DealerThread[];
  /** Flattened offer history across threads. */
  offers: Offer[];
  receipt_bundle_id?: string;
  created_at: IsoTimestamp;
  burned_at?: IsoTimestamp;
}

/** The per-deal relationship with ONE dealership. */
export interface DealerThread {
  /** → Dealership (GLOBAL). Also the thread's natural key within a deal (§4.4). */
  dealership_id: string;
  /** This dealership's specific car. Optional per D4 — absent during information_gather. */
  vehicle_instance?: VehicleInstance;
  /** Account-PRIVATE contact, embedded (D3). Optional per D4. */
  working_with?: DealershipContact;
  process_step: ProcessStep;
  messages: Message[];
  /** ADR-006: per-field newest-message-wins accumulation. */
  current_offer?: Offer;
}
```

### 2.6 Message (ratified shape, Q22) and Offer

```ts
/** Call metadata only. No audio exists to point at (specs/01; Q14). */
export interface CallMeta {
  started_at: IsoTimestamp;
  /** Unit-explicit (D9). Absent for a missed or still-running call. */
  duration_seconds?: number;
  /** The other end of the call, as known — number or name. Absent if withheld. */
  party?: string;
}

export interface Message {
  channel: MessageChannel;
  direction: MessageDirection;
  /** Who produced this text. Required — never inferred, never defaulted. */
  author: MessageAuthor;
  /** Verbatim for sms/email, authored for note. Absent for a bare call record. */
  body?: string;
  /** Present when `channel === 'call'` (§6 I-6). */
  call_meta?: CallMeta;
  timestamp: IsoTimestamp;
  /** ADR-005: may be partial. */
  extracted_offer?: Offer;
  // NOTE: there is no `recording_url` and no `transcript`. Not nullable — absent.
}

export interface OfferFee {
  name: string;
  amount: MoneyCents;
}

export interface Offer {
  /**
   * ADR-005: optional — absent means *the dealer did not state a price*
   * (a first-class, common state, not an error). Consumers must treat flags whose
   * inputs are missing as UNEVALUABLE, never default them to zero.
   */
  sale_price?: MoneyCents;
  fees: OfferFee[];
  /** Annual percentage rate, e.g. 6.9 — absent on cash deals. */
  apr?: number;
  term_months?: number;
  monthly?: MoneyCents;
  flags: OfferFlag[];
}
```

### 2.7 Write-once enforcement surface (AC-4)

Three mechanisms, each cheap, together leaving no silent-mutation path:

```ts
/**
 * True once the deal's make/model are locked: the deal has left `draft`, or any
 * offer is attached anywhere (specs/00 "Cardinality invariants":
 * "settable while the deal is `draft`, immutable once any offer is attached").
 * Pure and total — never throws, never reads a clock.
 */
export const isTargetVehicleLocked = (
  deal: Pick<Deal, 'status' | 'offers' | 'dealer_threads'>,
): boolean =>
  deal.status !== 'draft' ||
  deal.offers.length > 0 ||
  deal.dealer_threads.some((t) => t.current_offer !== undefined);
```

1. **Compile time:** `VehicleTarget.make`/`.model` are `readonly`, so `deal.target_vehicle.make = 'Toyota'` is a type error everywhere in the monorepo. The only settable form is `VehicleTargetDraft`, which exists solely at deal creation.
2. **Runtime:** `isTargetVehicleLocked` is the single predicate every write path consults. T-020 rejects the write and records the rejection as a receipt-trail event (specs/00 "Cardinality invariants"); T-016 mirrors the rule as a schema constraint. Neither invents its own condition.
3. **Structural:** `VehicleInstance` has no make/model at all, so "a thread whose car contradicts the deal anchor" is not a state the spine can hold (§6 I-2).

## 3. Adapter contracts — `packages/core/src/adapters.ts`

Unchanged in posture (specs/00: "Every external feed sits behind one internal interface. Core services never see a provider's shape"); changed only where the v0.5 vehicle split forces it. `AdapterErrorCode`, `AdapterError`, `AdapterResult`, `OutboundSms`, `OutboundEmail`, `ProviderSendReceipt`, `PrequalResult`, `CreditPrequalAdapter`, `VehicleDataAdapter`, `VehicleHistoryAdapter` keep their T-001 signatures verbatim.

```ts
/**
 * D12 — a valuation is ALWAYS of one specific car. `target` supplies the anchor
 * the instance deliberately lacks; `instance` supplies the priceable attributes
 * (year, trim, mileage, condition) specs/00 says no source can price without.
 * There is no overload accepting a bare make/model (AC-10).
 */
export interface ValuationRequest {
  target: VehicleTarget;
  instance: VehicleInstance;
}

export interface ValuationAdapter {
  readonly source: string;
  /** Implementations stamp `vehicle_instance_id = req.instance.id` on the result. */
  getValuation(req: ValuationRequest): Promise<AdapterResult<ValuationSnapshot>>;
}

/** A note is authored in-app and can never arrive from a provider webhook (D11). */
export type InboundChannel = Exclude<MessageChannel, 'note'>;

export interface InboundComms {
  channel: InboundChannel;
  /** Which of OUR identities the dealer contacted — routes to the Deal. */
  to_identity: { phone_number?: string; email_alias?: string };
  from: { phone?: string; email?: string };
  /** SMS/email body; absent for calls. */
  body?: string;
  /** For calls: the metadata that gets logged on the thread. No audio handle exists. */
  call_meta?: CallMeta;
  /** Provider's message id — idempotency anchor (§5.3). */
  provider_message_ref: string;
  received_at: IsoTimestamp;
}
```

`TelephonyAdapter` / `EmailAdapter` keep their T-001 signatures: `parseInboundWebhook(payload: unknown): AdapterResult<InboundComms>` stays **synchronous, pure, no I/O** — that is what makes ack-then-queue (§5.2) structurally forced rather than merely documented.

### 3.1 Cached, instance-bound records

**Module placement.** `ValuationSnapshot`, `VehicleData`, `VinDecode`, `RecallRecord`, and `VehicleHistorySummary` are **domain records**, so they live in `src/domain.ts`; `src/adapters.ts` imports them. They are documented in this section because the adapter contracts above are what produce them, not because they belong to the adapter module. The distinction is invisible to every consumer — downstream packages import all of it through the bare `@core` barrel (ADR-004/ADR-009) and never reach into a submodule path.

```ts
/**
 * ALWAYS of one specific car — never of a bare make/model (specs/00).
 * Bands are flat (D5) because ADR-007 names `ValuationSnapshot.retail` as the
 * `above_market` comparison basis.
 */
export interface ValuationSnapshot {
  vehicle_instance_id: string;
  wholesale?: MoneyCents;
  trade_in?: MoneyCents;
  /** ADR-007: the `above_market` reference band. */
  retail?: MoneyCents;
  private_party?: MoneyCents;
  /** Adapter id (e.g. "mock-kbb") — provenance, never a provider payload. */
  source: string;
  captured_at: IsoTimestamp;
}

/** Decode, recalls, history for one specific car. `reliability` is not modelled (D7). */
export interface VehicleData {
  vehicle_instance_id: string;
  /** Absent when the instance has no VIN — the normal launch case (Q16). */
  decode?: VinDecode;
  recalls: RecallRecord[];
  history?: VehicleHistorySummary;
  captured_at: IsoTimestamp;
}
```

`VinDecode`, `RecallRecord`, `VehicleHistorySummary` are unchanged from T-001 §2 (including their `fetched_at`, per D6).

## 4. Data shapes — how the pieces sit together

### 4.1 Reference graph

```
Account/owner  ──owns──▶  Deal ──1:1──▶ VehicleTarget         (make, model immutable)
                            │
                            ├─ dealer_threads[]  (one per dealership)
                            │     ├─ dealership_id ──ref──▶ Dealership        [GLOBAL]
                            │     ├─ vehicle_instance?  (embedded)            [account-private]
                            │     │      └─ id ◀──vehicle_instance_id── ValuationSnapshot
                            │     │                                    └─ VehicleData
                            │     ├─ working_with?  (DealershipContact, embedded) [account-private]
                            │     ├─ process_step
                            │     ├─ messages[]  (append-only, author-stamped)
                            │     └─ current_offer?   (ADR-006 rollup)
                            └─ offers[]  (flattened history across threads)
```

The only edge crossing the account boundary is `dealership_id → Dealership`, and it points at a record holding nothing but a name and a place. Everything a competitor account would want — who you talk to, which car, what they offered — is inside the deal.

### 4.2 Cardinality

| Relationship | Cardinality | Enforced by |
|---|---|---|
| Deal → VehicleTarget | exactly 1, make/model write-once | embedded field + `readonly` + `isTargetVehicleLocked` (§2.7) |
| Deal → DealerThread | 0..n, **≤1 per dealership** | `dealership_id` is the thread's key within the deal (§4.4) |
| DealerThread → VehicleInstance | 0..1 (D4) | embedded optional field |
| VehicleInstance → ValuationSnapshot | 0..n over time (snapshot + cache) | `vehicle_instance_id` |
| VehicleInstance → VehicleData | 0..1 current | `vehicle_instance_id` |
| DealerThread → Message | 0..n, append-only, ordered by `timestamp` | array; no mutator anywhere in core (§6 I-8) |

### 4.3 Two questions, two shapes (Q20)

| Question | Input | Output |
|---|---|---|
| "Can I afford it?" | `Deal.walk_away_number` vs an offer's out-the-door total | `over_walkaway` |
| "Is this a good price?" | `ValuationSnapshot.retail` **for this thread's instance** vs `Offer.sale_price` | `above_market` (ADR-007) |

Both inputs are reachable from a single `DealerThread` plus its `Deal`, and neither can be silently substituted for the other: the budget number lives on the deal and the band lives on a snapshot keyed by instance id. Missing either input yields **unevaluable**, never a pass (ADR-005 §2).

### 4.4 Notes for the persistence tasks (T-016/T-017) — not this task's code

- Natural key of a thread is `(deal_id, dealership_id)`; that composite is what makes "one thread per dealership per deal" a schema fact.
- `working_with` is embedded in the domain type; a normalized `dealership_contacts` table (T-016 AC-4) is a storage decision. Adding an `id` to the core `DealershipContact` type would be an ADR, not a mapping convenience.
- `Message` has no domain id (D15). Row ids are the store's; the extraction event's `message_ref` (§5) is the correlation handle across the bus.
- `captured_at` / `fetched_at` are wire and domain names; column naming is T-016's business.

### 5.2 Webhook ingest — ack-then-queue (unchanged rule, v0.5 payload)

specs/00: "webhooks ack immediately, all heavy work … runs on the event bus. Provider timeouts must never drop a dealer message." (AC-14 — unaffected by this migration, and the contracts keep forcing it.)

1. `adapter.parseInboundWebhook(payload)` — synchronous, pure. No DB, no extraction, nothing slow before the ack.
2. Wrap in `comms.inbound.received.v1`, **durably enqueue**.
3. **Ack 2xx** — meaning exactly "durably enqueued", nothing more.

| Failure | Behavior | Retry / idempotency | Logged | Surfaces as |
|---|---|---|---|---|
| Parse fails (`malformed_response`) | still ack 2xx; enqueue `CommsInboundQuarantinedV1` with `parse_error` + `raw_payload_ref` | none — quarantine/replay | code, source, ref | operator quarantine queue; **no** user-visible message loss |
| Enqueue fails (bus down) | **5xx** — the one deliberate non-ack | provider redelivers; dedupe on `source:provider_message_ref` | source, channel, outcome | nothing user-visible; provider retry is the durability mechanism |
| Provider redelivers | consumer treats equal `idempotency_key` as the same fact | at-least-once end to end | event_id, attempt | no duplicate thread entry |
| Inbound claims `channel: 'note'` | **not representable** — `InboundChannel` excludes it (D11); a provider payload that decodes to a note is a parse failure | none | code, source | quarantine, not a fabricated internal message |

Logged at ingest: source, channel, `provider_message_ref`, outcome. **Never logged:** message bodies, phone numbers, email addresses, raw provider payloads (there is no field on `AdapterError` where one fits).

## 6. Invariant touchpoints — what could break, and what stops it

| # | Invariant (source) | How this migration could break it | How the design protects it |
|---|---|---|---|
| I-1 | **One deal, one make/model; write-once** (specs/00 "Cardinality invariants"; Q11 AMENDED) | A mutable `target_vehicle`, or a second "current vehicle" field re-appearing | `readonly make`/`model` (compile-time), `VehicleTargetDraft` as the only settable form, `isTargetVehicleLocked` as the single runtime predicate (§2.7); `resolved_vehicle` deleted outright (§1) |
| I-2 | **A thread's car cannot contradict the anchor** (specs/00; Q11 AMENDED) | Adding make/model to `VehicleInstance` "for convenience" | `VehicleInstance` structurally has no make/model — the contradictory state is unrepresentable, so the rejection path is about *input*, not stored data. **Builders must not add these fields.** |
| I-3 | **Honesty of the verdict: fair price is per instance** (specs/00 "Budget ceiling vs. fair price"; Q20) | A `ValuationSnapshot` of a bare make/model sneaking back in | `vehicle_instance_id` is required on the snapshot and `ValuationRequest` requires a whole `VehicleInstance` (D12) — there is no call shape that prices a make/model |
| I-4 | **Missing input ⇒ unevaluable, never zero** (ADR-005; ADR-007) | Defaulting an absent band or price to 0 to keep a flag "green" | `sale_price?`, all four bands `?`, `vehicle_instance?` — every absence is typed as absence, and §5.3 names the unevaluable outcome for each; core exports no default/coalesce helper |
| I-5 | **Dealership tenancy split** (specs/00 "Dealership data tenancy"; Q12 AMENDED) | Re-adding `staff[]` to `Dealership`, or making contacts globally addressable | `Dealership` has no people and no account field; `DealershipContact` has no id and no account field because it lives inside the account-owned thread (§2.4, D2/D3) — there is no global contact row to leak |
| I-6 | **No audio, ever** (specs/01 "Consent & recording posture"; Q14) | A nullable `recording_url`, a `call_ref` audio handle, a transcript field | All three deleted (§1). `CallMeta` carries time/duration/party only. The transcription events are gone, so nothing on the bus can request audio work; reviving it needs a new decision plus an approved provider |
| I-7 | **Author is never inferred** (specs/00 "Receipt layer"; Q22; Q21 mitigation) | Defaulting `author` from `direction`, or letting a provider payload become a `note` | `author` is required with no default; `InboundChannel = Exclude<MessageChannel,'note'>` makes provider-sourced notes unrepresentable (D11) |
| I-8 | **Receipt trail is append-only** (specs/00 "Receipt layer") | An update/delete surface entering core during a large rewrite | Core still exports zero mutators; the package's own invariant test greps its exports and sources for `update|delete|remove|mutate|purge|redact|overwrite` (§7) |
| I-9 | **Webhooks ack immediately; no dropped dealer message** (specs/00; AC-14) | Making `parseInboundWebhook` async, or adding a synchronous heavy adapter method | Parse stays sync + pure; all heavy work exists **only** as event types; §5.2's decision table is unchanged from T-001 §5.2 apart from the quarantine payload |
| I-10 | **`identity_ref` provider-agnostic** (specs/00; AC-15) | A provisioner/vendor field arriving with the Dealership work | `IdentityRef` untouched by this migration; the package test asserts no provider-ish key exists on it |
| I-11 | **Spine defined once** (ADR-001; AC-16) | A compatibility `VehicleSpec` alias left behind so downstream keeps compiling | §1 is a delete list, not a deprecate list; the existing repo-wide grep test extends to `VehicleTarget\|VehicleInstance\|Dealership\|DealershipContact` outside `packages/core` |

| I-14 | **No silent interpretive drift** (CLAUDE.md #3) | Unlogged shape decisions in a large rewrite | §0 logs all seventeen with their basis; the three judgement calls with the widest blast radius (D4 and D16 optionality, D7 omission) are also reported as deviation notes to the chief |

## 9. Deviations and blockers

**Blocked: no.** No frozen-spine change, no unapproved integration, and no foreign file is required. Three judgement calls are recorded for the chief's awareness; all are resolved inside spec ambiguity and none stops the build:

1. **D4 — `vehicle_instance?` / `working_with?` optional on `DealerThread`.** specs/00's model block writes them without `?`, but `process_step: information_gather` necessarily precedes knowing the specific car or the person. Requiring them would force fabricated values into the receipt trail. Handled honestly by the spec's own rule: no instance ⇒ no snapshot ⇒ fair-price **unevaluable**, never "fine". If the chief prefers them required, the change is one character each plus a T-020 creation-order rule.
2. **D7 — `VehicleData.reliability?` omitted.** specs/00 v0.5 lists the field, but nothing in the specs, ADRs, or adapter layer defines its shape (its named source is a repair ledger that does not yet exist). Inventing one would be interpretive drift; the field is additive and non-breaking whenever a shape is specified.
3. **D16 — `Message.body` optional.** specs/00's ratified `Message` block writes `body` unqualified while marking two sibling fields optional, so this is a departure from the literal block. A `channel: 'call'` message has no text at all — only `call_meta` — and requiring `body` would put `body: ''` into an append-only receipt trail. Typed absence is the honest encoding, and the `call_logged` alert (D14) is what moves that message out of the empty state. One character to reverse if the chief prefers a call message to be unwritable until its note exists.

Also worth the chief's eye (not deviations — mechanical consequences already authorized by the task EXTRA and ADR-007/D6): the `ValuationSnapshot` band flattening and the `fetched_at → captured_at` rename widen T-013's edit surface slightly, and D10's `dealer_id → dealership_id` / `message_ref` rename widens T-012's and T-014's. Both are inside the "deliberately breaking, downstream tasks fix their own packages" envelope the task sets.
