## 0. Interpretive calls made by this design (drift trip-wire log)

Each call stays inside spec/ADR ambiguity or is a mechanical consequence of the toolchain. None touches a protected path. A builder that finds any of these insufficient **stops and messages the lead** — it does not improvise, and above all it does not add a dependency or edit a foreign file.

| # | Call | Basis / consequence |
|---|------|---------------------|

Registration happens by *creating the manifest*, not by touching the glob list. | ADR-003 "Decision" (workspace declaration lives in root `package.json` with those globs). AC-1 is satisfied by the existing globs; a needless edit to a shared root array is churn on a contended file. |
| **D2** | **A fourth alias, `@comms` → `services/comms/src/index.ts`, is added** alongside `@db`, `@store-pg`, `@object-store`. | **Necessary, not optional.** T-017 must implement `CommsStore` / `RawPayloadStore` — those types are declared in `services/comms/src/ports.ts` and re-exported from `services/comms/src/index.ts`. T-019 must import `createCommsService`, `InMemoryQueue`, `InMemoryCommsStore`. | **D4** | **`services/api` gets no path alias.** It is a workspace member and a *consumer* of aliases; nothing imports a service except through `@comms`, which exists only because T-014's ports have no other home. | Follows the `services/comms` precedent (T-001 §1.3: "nothing imports a service"). If a later epic needs to import the API, that is a superseding change to this file. |

**T-015 exports no TypeScript value and declares no TypeScript type.** What it *fixes* is the module graph: which specifiers resolve, to what, and who may import whom. That graph is this task's interface, and it is binding on T-016–T-020.

### 2.2 Import-direction law (binding on T-016–T-020)

```
@core            ← everything.  Defines the spine.  Depends on nothing.
@comms           ← @store-pg, services/api.        Declares the ports.  Depends on @core.
@db              ← @store-pg, services/api.        Owns `pg` + migrations.
@object-store    ← @store-pg, services/api.        Owns `@aws-sdk/client-s3`.
@store-pg        ← services/api.                   Implements @comms ports over @db (+ @object-store refs).
services/api     ← nothing.                        Composition root.  Owns `fastify` + `zod`.
```

Rules that follow, each of which is a review finding if broken:

1. **No new spine type, anywhere.** `Deal`, `DealerThread`, `VehicleTarget`, `VehicleInstance`, `Dealership`, `DealershipContact`, `Message`, `Offer`, `ValuationSnapshot`, `VehicleData` and every enum on them are **imported from `@core`**, never re-declared, never widened, never mirrored as a "row type that happens to match". ADR-001: defined once, imported everywhere.
2. **No new port type.** `CommsStore`, `CommsStoreReader`, `RawPayloadStore`, `EventQueue`, `StoredMessage`, `QuarantinedRecord`, `UnroutedRecord`, `ConsumeResult`, `EnqueueResult`, `EventHandler`, `DeadLetter`, `RollupContribution`/`RollupState`, `ConsentHook`, `OutboundPort` are **imported from `@comms`**. T-017 must annotate its implementation with the imported type (`class PgCommsStore implements CommsStore`) so a port drift in T-014 breaks the build rather than passing structurally.
3. **No provider shape crosses a barrel.** `pg`'s `Pool`/`QueryResult`/`PoolClient`, the S3 SDK's `PutObjectCommand`/`GetObjectOutput`, and Fastify's `FastifyRequest`/`FastifyReply` must not appear in any *exported* signature of `@db`, `@store-pg`, or `@object-store`. specs/00: "Core services never see a provider's shape." The per-package dependency placement (D3) makes the violation visible in a manifest diff.
4. **`@db` is the only module that constructs a `pg` connection.** `@store-pg` receives a handle; it does not read `DATABASE_URL`.
5. **Row shapes stay inside `@store-pg`.** Reads assemble `@core` aggregates before returning (T-017 AC-9).

### 2.3 Barrel obligation

Each of `@db`, `@store-pg`, `@object-store` must be satisfied by **exactly one** `src/index.ts` that is the package's whole public surface. Field-level shapes are owned by T-016/T-017/T-018 designers; what T-015 fixes is that the composition below must typecheck **without a cast and without a locally-declared structural stand-in**:

```ts
// services/api — composition root, illustrative shape.  Names owned by T-016/T-017/T-018/T-019;
// the TYPE IDENTITIES (CommsStore, RawPayloadStore, EventQueue, and every @core aggregate) are
// fixed here and are not open to re-declaration.
import type { CommsStore, EventQueue, RawPayloadStore } from '@comms';
import { InMemoryCommsStore, InMemoryQueue, InMemoryRawPayloadStore, createCommsService } from '@comms';

// Postgres path — selected only when DATABASE_URL is present (ADR-008).
const store: CommsStore = process.env.DATABASE_URL
  ? /* from @store-pg, over a handle from @db */ ({} as CommsStore)
  : new InMemoryCommsStore();

const payloads: RawPayloadStore = /* @object-store when configured, else */ new InMemoryRawPayloadStore();
const queue: EventQueue = new InMemoryQueue(); // managed queue stays unwired this epic (AC-4)

createCommsService({ store, raw_payloads: payloads, queue /* … */ } as never);
```

The load-bearing property: **`store` is annotated `CommsStore`.** Substituting Postgres for in-memory is an assignment, not a redesign — which is exactly what T-009 §3 promised and what makes ADR-008's "swapping to Postgres is configuration, not a code change" true rather than merely stated.

### 2.4 Library type surfaces this task makes resolvable

These are the *only* third-party type surfaces Epic 2 acquires. Each is confined to the package that declares the dependency (D3):

```ts
// packages/db, packages/store-pg — pg is CommonJS; under root "type": "module" use the
// default-import form for VALUES, and the named form for TYPES (see §4.5).
import pg from 'pg';                       // const { Pool } = pg;
import type { Pool, PoolClient, PoolConfig, QueryResult, QueryResultRow } from 'pg';

// packages/object-store
import { S3Client, PutObjectCommand, GetObjectCommand, HeadObjectCommand } from '@aws-sdk/client-s3';

// services/api
import Fastify from 'fastify';
import type { FastifyInstance, FastifyRequest, FastifyReply } from 'fastify';
import { z } from 'zod';
```

Nothing else enters. No ORM, no query builder, no migration framework, no queue client, no auth SDK, no HTTP client, no logger, no test-container library. ADR-008 chose plain `.sql` + a small in-repo runner precisely so the tenancy split and the append-only receipt rule stay visible in raw SQL rather than hidden behind a model layer — a builder that reaches for Prisma/Drizzle/Knex to "save time" is reversing a ratified decision.

Two notes for the builder:

- The trailing `npm run typecheck --workspaces --if-present` is the permanent, member-agnostic half (D5). It is a no-op today and becomes coverage the moment a member declares its own script.

### 3.2 The four new manifests (exact)

```jsonc
// packages/db/package.json
{ "name": "@deal-copilot/db", "private": true,
  "dependencies": { "pg": "^8" },
  "devDependencies": { "@types/pg": "^8" } }

// packages/store-pg/package.json
{ "name": "@deal-copilot/store-pg", "private": true,
  "dependencies": { "pg": "^8" },
  "devDependencies": { "@types/pg": "^8" } }

// packages/object-store/package.json
{ "name": "@deal-copilot/object-store", "private": true,
  "dependencies": { "@aws-sdk/client-s3": "^3" } }

// services/api/package.json
{ "name": "@deal-copilot/api", "private": true,
  "dependencies": { "fastify": "^5", "zod": "^4" } }
```

- Names follow ADR-004 §1 (`@deal-copilot/<name>`); the *aliases* stay bare (`@db`, not `@deal-copilot/db`). Both forms coexist by design and always have.
- No `main`, no `exports`, no `types`, no `version`, no `files`. These are workspace markers, not publishable packages (`"private": true`). Cross-package resolution is by tsconfig `paths` + the vitest alias map, never through `node_modules` (T-001 §1.2).
- No cross-package `dependencies` entries (`"@deal-copilot/core": "*"` etc.) — they would imply npm-graph resolution that does not exist here and would create install-order coupling for nothing.
- Ranges resolve, at time of writing, to `pg` 8.22, `@types/pg` 8.21, `@aws-sdk/client-s3` 3.1106, `fastify` 5.11, `zod` 4.4. The builder records the resolved versions in the commit message; a major that differs from the caret above is a note to the lead, not a silent re-range.
- **`@types/node` is deliberately not declared.** It arrives transitively via `@types/pg` and is reachable by explicit `/// <reference types="node" />` from library typings even though `tsconfig.base.json` sets `"types": []` (which only disables *automatic* inclusion). Consequence in §5.7 — it constrains what the new packages may do about Node globals.

### 3.3 Alias maps (both files, entry-for-entry identical — binding)

`tsconfig.base.json` `compilerOptions.paths` gains, in this order after the existing eight:

```jsonc
"@comms":        ["services/comms/src/index.ts"],
"@db":           ["packages/db/src/index.ts"],
"@store-pg":     ["packages/store-pg/src/index.ts"],
"@object-store": ["packages/object-store/src/index.ts"]
```

`vitest.workspace.ts` `alias` gains the same four, same order, same targets, through the existing `r()` helper:

```ts
'@comms':        r('services/comms/src/index.ts'),
'@db':           r('packages/db/src/index.ts'),
'@store-pg':     r('packages/store-pg/src/index.ts'),
'@object-store': r('packages/object-store/src/index.ts'),
```

**Sync rule (inherited from T-001 §1.4, restated as binding on this change):** the two maps must stay entry-for-entry identical — same keys, same order, same targets. Drift means tests and typecheck disagree about what a specifier means, which is the worst possible failure because it is silent in both directions. The T-001 header comment in `vitest.workspace.ts` names T-001 as the owner of both files; the builder **updates that comment** to record that T-015 extended the map under the same rule (it is a comment in a T-015-owned file, not a foreign edit).

### 3.4 The four new `tsconfig.json` files (identical to the existing house shape)

```jsonc
{ "extends": "../../tsconfig.base.json", "include": ["src", "test"] }
```

for `packages/db`, `packages/store-pg`, `packages/object-store`; and for `services/api` the same (`../../tsconfig.base.json` — `services/api` is also two levels deep).

**No per-package `compilerOptions` override.** `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes` are the one shared toolchain (ADR-001). Third-party typings are optional-heavy and will create friction — `skipLibCheck: true` absorbs it inside `node_modules`, and friction in *our* code is handled in our code. A downstream task that wants to relax a compiler option is asking for a toolchain change: **escalate**, do not override locally.

### 3.5 Environment contract (D6 — names registered, nothing implemented)

ADR-008's posture, made concrete so four tasks agree:

| Variable | Absent ⇒ | Present ⇒ |
|---|---|---|

## 4. Error paths per operation

T-015's operations are toolchain operations. Each is stated with its failure mode, whether a retry is safe, what gets recorded, and what surfaces to the lead. §4.4–§4.6 are the runtime failure rules the *dependency choice* imposes on downstream tasks — they belong here because they are consequences of ADR-008's posture, which this task instantiates.

### 4.1 `npm install` at root (the one sanctioned install)

| Failure | Retry / idempotency | Recorded | Surfaces as |
|---|---|---|---|
| Registry unreachable / ETIMEDOUT | Safe to retry — `npm install` is idempotent given identical manifests | nothing written on failure | blocker to lead if it persists; **never** work around by vendoring or by hand-editing `package-lock.json` |
| `EINVALIDPACKAGENAME` | Not retryable — manifest bug (ADR-004 §1: bare `@db` is not a legal npm name; the manifest name is `@deal-copilot/db`, only the *alias* is bare) | manifest diff | fix the manifest, re-run |
| Peer/engine conflict between the four libs | Not retryable | resolution tree | **escalate** — do not add `--legacy-peer-deps`, do not add a resolution override; a peer conflict means ADR-008's set needs an amendment |
| Lockfile churn beyond the four subtrees (unrelated transitive bumps) | n/a | `git diff --stat package-lock.json` | expected and acceptable — the lockfile is a single root artifact (ADR-004 §2) and a full regeneration is its normal state. Report the top-level added packages in the commit message so a reviewer can check the list against ADR-008 without reading the lockfile. |
| A fifth top-level package appears in `dependencies` anywhere | n/a | manifest diff | **hard stop.** CLAUDE.md invariant 2 ("no unapproved integration"). Transitive packages are fine; a new *declared* dependency is not. |

Determinism: after this task, `npm ci` from a clean tree must reproduce the same tree. The builder verifies with `npm ci` (or `npm install` a second time producing no lockfile diff) before committing.

### 4.2 `npm run typecheck`

| Failure | Meaning | Response |
|---|---|---|
| `TS18003` / `TS18002` on a new member | An empty project was handed to `tsc` | Design error, not a code error — the four new members must not be in the explicit chain (D5). Fix the script. |
| `TS2307 Cannot find module '@db'` from a *new* package's future source | Alias missing or the two maps drifted | Compare §3.3 entry-for-entry in both files |
| A pre-existing member fails | Half-A migration in flight (T-010…T-014) | **Not T-015's to fix.** Record which project and the first error; report to the lead; do not edit the foreign package |
| `TS2688 Cannot find type definition file for 'node'` | `@types/node` did not arrive transitively | See §5.7 — this is the one case where a fifth `devDependencies` entry (`@types/node`) may be warranted, and it is an **escalation to the lead**, not a unilateral add |

### 4.3 `npx vitest run` (root)

`include` is unchanged, so the new members contribute zero test files and vitest reports the existing suite exactly as before. A "no test files found" outcome would only occur if the root suite were empty, which it is not. Alias additions cannot break existing resolution — the four new keys collide with nothing.

**ADR-008 skip rule, restated as binding on T-016/T-017/T-018:** a test that requires Postgres or a live object store is written with an explicit skip guard on the environment variable. A skipped test is reported as **skipped**. It is never reported as passed and it is never quietly deleted — "silently green tests over an absent database would be a lie about coverage" (ADR-008). Deleting a DB test to make CI green is a receipt-layer-grade honesty failure and a review reject.

### 4.4 Store selection at API startup (downstream rule, fixed here)

The posture ADR-008 sets is *default to in-memory*, **not** *fall back to in-memory*. The difference is the whole point:

| State | Behaviour |
|---|---|
| `DATABASE_URL` absent | Compose in-memory. Log once, at startup, plainly: persistence is in-memory and data does not survive restart (ADR-008 "Consequences"). |
| `DATABASE_URL` present, connection succeeds | Compose `@store-pg`. |
| `DATABASE_URL` present, connection **fails** | **Fail fast — exit non-zero.** Never fall back to in-memory. A configured-but-unreachable database that silently degrades to a volatile store would accept a dealer message, return 2xx, and lose it — violating specs/00 "Provider timeouts must never drop a dealer message" while *looking* healthy. |
| `OBJECT_STORE_BUCKET` present but endpoint/region incoherent | Fail fast at startup, same reasoning. |

Idempotency of the composition itself: building the app is a pure function of environment + code; there is no partial-composition state to clean up because the process exits.

### 4.5 CommonJS/ESM interop for `pg` (mechanical, and it will bite)

Root is `"type": "module"`. `pg` is CommonJS. Named-import interop for CJS depends on Node's static export detection and is not guaranteed for `pg`'s export shape:

```ts
import pg from 'pg';            // ✅ values
const { Pool } = pg;
import type { Pool } from 'pg'; // ✅ types (@types/pg declares named types)
import { Pool } from 'pg';      // ⚠️ may typecheck and fail at runtime — do not use for values
```

`fastify`, `zod`, and `@aws-sdk/client-s3` ship dual ESM/CJS builds and take normal named imports. This is recorded here because it is a dependency-choice consequence and the failure is a *runtime* `SyntaxError` that typecheck will not catch.

### 4.6 Starting the API process (D7 — open, handed to T-019)

There is no emit step (T-001 D5) and no TS runtime loader (D7). Two consequences T-019's designer must resolve **without adding a dependency**:

1. Bare aliases (`@core`, `@comms`, …) are a *TypeScript and vitest* mechanism. Node resolves neither. Anything that runs under plain `node` cannot use them.
2. Node 24 strips types natively, but does not rewrite specifiers, so a `./x.js` specifier must correspond to a real file.

The path that needs neither: **`services/api` exports a `buildApp()` factory and its tests drive it through Fastify's in-process `inject()`.** That satisfies "the service starts and serves" (T-019 AC-12) with no loader, no port binding, and no new dependency. If T-019 concludes a real listening process is required for the deliverable, the loader question goes to the lead as an escalation — T-015 pre-registers nothing.

### 4.7 Git (shared tree)

Stage only the twelve owned paths, explicitly — never `git add -A`, never `git add .`, never `checkout`/`reset`/`stash`. `package-lock.json` must be staged by name; it is large and easy to miss, and an unstaged lockfile makes the commit non-installable. Retry up to 5× on `index.lock` (T-010…T-014 are committing into the same tree). Commit message: `T-015(builder): <what>`, including the resolved versions of the five installed packages.

How a task that adds *no code* still protects the spine — by controlling what code downstream is able to write.

| # | Invariant | Source | How this design protects it |
|---|---|---|---|
| 5.1 | Fleet cannot mutate its constitution | CLAUDE.md invariant 1 | Ownership is twelve enumerated files. `CLAUDE.md`, `thesis.md`, `specs/**`, `.claude/**` are untouched; the PreToolUse hook is the backstop, ownership discipline is the intent. |
| 5.2 | No unapproved integration or spend | CLAUDE.md invariant 2 | Exactly five installed packages, each a *client library for an already-approved integration*: `pg` + `@types/pg` → Postgres (specs/00 Store); `@aws-sdk/client-s3` → S3-compatible object store (specs/00 Store); `fastify`, `zod` → Node/TS backend (specs/00 Stack, ADR-001). **No managed-queue client** — specs/00 "Async backbone" names the bus and leaves the provider open, so the in-memory `EventQueue` stands this epic (AC-4). **No auth SDK** — specs/00 Stack lists Auth0/Clerk/Cognito as unchosen alternates. **No valuation, history, or credit SDK** — those targets are mock-only until Corban signs, and their absence from `package-lock.json` is the structural proof. Concentrating dependency authority in one task makes "a new dependency appeared" a one-file diff a reviewer cannot miss. |
| 5.3 | No silent interpretive drift | CLAUDE.md invariant 3 | ADR-008 pre-logged all five library choices *and* the storage posture, so the build implements a decision rather than making one. Everything this design adds beyond ADR-008 is logged as D1–D7, with D2 and D5 flagged to the lead. |
| 5.4 | Spine defined once, imported everywhere | ADR-001; T-001 D2/D3 | §2.2 rules 1–2 forbid re-declaring any `@core` type or any `@comms` port. Bare-only aliases make deep imports unresolvable, so no downstream package can reach past a barrel to a "convenient" internal type. |
| 5.5 | Anti-corruption boundary — core services never see a provider's shape | specs/00 "Integrations — adapter layer" | Per-package dependency placement (D3): `fastify`/`zod` cannot legitimately appear in `@db`; `pg` cannot legitimately appear in `services/api`; the S3 SDK lives in one package. npm hoisting means a stray import still *resolves* — so this is a **review invariant, mechanically checkable**: every non-builtin, non-alias import in package *X* must appear in *X*'s `dependencies`. §2.2 rule 3 forbids provider types in exported signatures. |
| 5.6 | Cardinality + tenancy invariants stay enforced by the schema | specs/00 "Cardinality invariants", "Dealership data tenancy" | The one-vehicle-per-deal anchor, the global-`Dealership`/account-private-`DealershipContact` split, and the append-only receipt trail are enforced in SQL by T-016. The dependency set is chosen so they *can* be: plain `.sql` + a small runner keeps constraints, grants, and the absence of an UPDATE/DELETE path readable in the migration files. Adding an ORM would relocate those rules into a model layer where a reviewer cannot see them — which is precisely why ADR-008 rejected Prisma/Drizzle, and why an ORM appearing in a later diff is a reject, not a preference. |
| 5.7 | One shared toolchain; no local escape hatches | ADR-001 "Consequences" | Every new `tsconfig.json` extends the base with `include` only (§3.4). Two live consequences: (a) `"types": []` means Node globals are not ambient — the four new packages **must not** hand-write a `node-shim.d.ts` the way `services/comms` did, because `@types/node` is present transitively via `@types/pg` and pulled into any program that touches `pg`/`fastify`/the S3 SDK; a hand-written `declare module 'node:crypto'` would then collide as a duplicate identifier. (b) If `@types/node` turns out *not* to be reachable, the fix is one root `devDependencies` entry — an escalation (§4.2), never a per-package compiler-option override. |
| 5.8 | Missing input ⇒ UNEVALUABLE, never zero | ADR-005; specs/00 "Budget ceiling vs. fair price" | `zod` is the validator, and it is the one library that can quietly manufacture data. **Binding on T-019/T-020:** no schema for `Offer.sale_price`, `apr`, `term_months`, `monthly`, `fees`, or any valuation field may carry `.default(0)`, `.catch(0)`, or a coercion that turns absent into zero. Absent means absent; a flag whose input is absent is *unevaluable*. Likewise `@store-pg` must map SQL `NULL` to `undefined`, never to `0`, and a thread with no `ValuationSnapshot` reports fair-price as unevaluable, never "fine". |
| 5.9 | `current_offer` is per-field newest-wins | ADR-006 | The rollup lives in `@comms` (`mergeCurrentOffer`) and is imported, not reimplemented. §2.2 rule 2 forbids a parallel rollup in `@store-pg`; persistence stores the rollup's *output*, it does not recompute the policy in SQL. |
| 5.10 | `above_market` compares to the RETAIL band; per-`VehicleInstance` | ADR-007; specs/00 "Budget ceiling vs. fair price" | No dependency here computes valuation, and none may. `ValuationSnapshot` rows are stored against a `vehicle_instance_id` (T-016) — the schema must make a deal-level valuation unrepresentable, because a make/model-level price is exactly the thing the spec says cannot exist. |
| 5.11 | Webhooks ack immediately; a dealer message is never dropped | specs/00 "Comms aggregation layer" | `fastify` is a server framework only; the ack-then-enqueue sequence is T-019's. The dependency-level guarantee is that **nothing was installed that invites inline work on the request path** — no extraction library, no valuation client, no mail/SMS SDK. The fail-fast rule in §4.4 protects the same promise from the other side. |
| 5.12 | No audio, ever | specs/00 Store ("No audio is stored"); specs/01 consent posture | The object-store dependency is a generic S3 client; T-018 must expose no audio method and no audio content type. Nothing in this dependency set (no transcription SDK, no media library, no speech client) makes an audio path convenient — the easiest thing to build remains the compliant thing. |
